# Changelog

## Unreleased (0.5.0)

### Security (fixes for 0.4.x, see the [security advisory](https://github.com/Atlas-Authorization/pca/blob/main/docs/pca/advisories/2026-11-pca-0.4.x.md))

- **Budget allocations (fixed in 0.5.0; 0.4.3 and earlier affected).** A delegation chain whose child carried a larger `budget_alloc` than its parent passed chain verification; only a non-negative limit was checked. A widening chain now fails.
- **`zk_compliance` (fixed in 0.5.0; 0.4.3 and earlier affected).** A PCActn carrying `zk_compliance` passed the core verifier and the signature-only guards with no zero-knowledge verifier checking it. It now fails unless a verifier enforced it.

- **Breaking, security (fail-open fixes):**
  - `IntentV2.Decide` now enforces rule 22 and grant action pins, as the reference does: a v2 schema with forged floors or traits is refused (`schema_floor_forged`), a grant carrying `envelope.actions` is checked (`pin`), and the floors meet the grant (`traits`: a verb above `max_esc` is denied, a tier above `preauth_esc` or a missing caveat or context key escalates). Before this a forged v2 schema was accepted and a pin ignored. `reviewers`, `call_context` and `actions` in the verifier context are validated. Grants with a pin now need a schema and the plaintext params.
  - The MAA x5c, GCP x5c and NVIDIA device and RIM signer chains now apply the strict chain profile (CA roles and no unrecognised critical extension). Before this a chain under a pinned root passed with a non-CA intermediate, a keyUsage without keyCertSign, an exceeded pathLen, a CA:TRUE leaf or an unknown critical extension.
  - MAA and GCP tokens: an RS256 token under an RSA-PSS restricted key is refused (the signature does not verify). Before this a PKCS#1 v1.5 signature under such a key passed.
  - MAA and GCP tokens: a header or payload segment nested past 512 levels is refused with `nesting too deep`. Before this the wording of the refusal recursed without a limit, and a large enough segment overflowed the stack and killed the process.
  - GCP Confidential Space: a JWK whose RSA n/e or EC x/y is not the key of its x5c leaf is refused. Before this an attacker key beside any genuine (public) chain was trusted whenever a root or SPKI anchor was configured: full attestation forgery.
  - Attestation certificates: a serial or version INTEGER that is empty or carries a redundant leading 00 or FF octet is refused, as OpenSSL refuses it, and so is an RSA-PSS salt length or trailer field that is negative, empty or non-minimal. Before this such a certificate was parsed and its PSS signature could verify.
  - A PCActn carrying `bond_ref` is denied through `Authorize` (`bond: unsupported`) unless `AllowUnsupported` lists `bond`; it never reports a pass.
  - Carried `budget_alloc` limits must be non-increasing down the chain (a widening fails the chain check).
  - A PCActn carrying `zk_compliance` fails at the core verifier and the signature-only guard too, not only `Authorize`.
  - A blueprint record with `runtime_pins` was refused as `bad_record`, so its key stayed unregistered and mode `any` allowed the chain. It is now accepted and its instances deny (`admission_required`); `BlueprintRegistry` is safe under concurrent calls.
  - A need's scope with U+FEFF is `bad_field` (JS whitespace semantics; U+0085 is no longer refused); the push token comparison is constant-time.
  - The ASP.NET Core middleware takes `AllowedSuites` and forwards it in both modes; `PcaAuthorizeOptions.AllowUnsupported` is new.
  - Intel collateral reads `tcbInfo` and `enclaveIdentity` from the signed bytes. Before this a later duplicate member replaced the signed body, so an out-of-date or revoked platform could report UpToDate.
  - AMD: `trustAnchorArkSpkiSha384` in a verifier configuration is ignored; the pin comes only from `family`.
  - Attestation configuration: a malformed optional allowlist (`hostData`, `chipIds`, `fmspcs`, `rtmrs`, `acceptStatuses`, the MAA lists, the GCP lists, the NVIDIA deny lists and `requireCrlIssuers`) refuses the configuration; before this it could read as no list. `minTcbEvaluationDataNumber` given as a numeric string is now enforced.
  - OCSP: a malformed `nextUpdate` or embedded certificate rejects the response, a PKCS#1 signature under an rsa-pss key is refused, and a delegated responder must pass the issuer check (name, key identifier, keyCertSign).
  - OCSP: a delegated responder whose authority key identifier names another issuer is refused: its serial and directory name are compared, not only its key id, also when the issuer has no subject key identifier. A malformed or repeated key identifier on the responder or the issuer is refused too. Before this only a leading key id was compared.
  - Certificate signatures: a certificate whose outer signature algorithm differs from the one inside `tbsCertificate` is refused, as `X509_verify` does.
  - NVIDIA: a non-string `leafSubjectIncludes` is coerced to its string form and enforced; before this it was skipped.
  - NVIDIA collateral: by default every chain certificate that names a CRL distribution point must be covered by a verified CRL from its issuer; previously any one fresh CRL satisfied the check (a prover supplying only the root's CRL left the device certificates unchecked). New option `requireCrlFor` (`cdp` default, `all`, or a list of chain indices) on the NVIDIA collateral hook; it applies only where CRLs are required (`revocation` `crl` or `both`, or `requireCrls` not `false`), and a malformed value is refused at construction.
  - Revocation non-membership: a leaf without an `id` or a non-object `lo`/`hi` is refused. Ledger consistency: the path bound is 108 and a missing or non-array `path` is refused.
  - Plan lifecycle: a grant id with a lone surrogate has no store key and is refused; before this it read the plan of the grant `\uFFFD`. Keys encode like `encodeURIComponent` (`!*'()` stay literal), so a stored plan whose grant holds one of those characters reads as unknown.
  - NVIDIA RIM: a non-string `minDriverVersion` or `minVbiosVersion` refuses the configuration (before this it set no floor). XML nesting over 256 levels fails closed instead of ending the process, and parsing is linear in the document size.
  - NVIDIA RIM XML: element and attribute names must match the reference parser's name pattern; before this `<!doctype x="1"/>` inside a document read as an element, not a DOCTYPE. A DOCTYPE is recognised in any case. `&#+65;` and `&#x+41;` are refused; before this they decoded to `A`. An `xml:*` attribute now gives the profile reason, not an unbound-prefix error. Line endings and literal whitespace in attribute values are normalised as the reference parser does, so a signed CRLF document digests the same. An explicit `xmlns:xml` declaration is rendered in the canonical form, as the reference does.
  - NVIDIA OCSP: a constructed `[0]` certStatus no longer reads as good and an unknown element after `thisUpdate` no longer skips the stale check. Parsing has the same depth, node count and size limits as the reference, and a deep nesting fails closed instead of ending the process.
  - Issuing: `MintGrant` refuses a malformed `risk_policy`, `units`, `tighten`, `template_ref`, `actions`, `model_polarity` or `provenance` and keeps only the envelope's known members. `SignPassport` requires evidence for any truthy `hardware_rooted` and safe-integer times, including `evidence.at`. `BuildPCActn` treats `params_digest: null` as a mismatch.
  - Sigstore: only P-256 and P-384 leaf keys verify; before this any 256-bit curve did. The TBS and outer signature algorithms must agree on every certificate, not only the leaf. An offset minute over 59 and years 0000-0099 are refused in timestamps. Ed25519 issuer keys are read from the certificate.
  - Bundles: a malformed `shadow` list is refused. Middleware: an empty `pca-fresh-at` header is a bad token, not a missing one.
  - Receipts and wallets: `A2a.VerifyReceipt` refuses an absent `prev`. `K4.VerifyGranted` no longer reads a non-string `tokenAddress` as native or compares missing `chainId`/`to` as equal. `K4.LooksLikePan` treats U+FEFF as whitespace. `AuthorizeInput.EscalationRequestTtlMs` is `long?`: null is one hour and 0 now expires at once.
  - Revocation freshness: `StalenessWindows` keeps `rate_limited` separately (new optional parameter `RateLimited`), so a malformed `costly` beside a valid `rate_limited` is refused and each error names the right member. The window read is `rate_limited ?? costly ?? max`.
  - `Authorize`: `Require` naming `bond` with `AllowUnsupported` listing it, or naming `provenance_flow`, now denies as the reference does (`bond: required check is unsupported`, `provenance_flow: required check is absent`). Before this the later status overwrote the required failure, so the call was allowed, even when the provenance gate was not enforced (`insecure_off`).
  - `LeasePolicy.MaxTtlCeiling` (new): a longer `max_ttl` is refused (`ttl_ceiling`) and past revocations are pruned; `LeaseRegistry` takes an optional clock.
- **Breaking, 0.5 hardening (every item is a behaviour change you may have to act on):**
  - `Pca.VerifyPcactnCore` / `VerifyRaw` take a final `PlanRootPolicy? planRoots` and check `plan_root_authorized` at the core: `new PlanRootPolicy(AuthorizedRoots: [...])` passes only a listed plan root (a list given, even empty, is enforced and wins over the skip), `PlanRootPolicy.Skip` is the explicit opt-out (reported `not-enforced`, `Verdict.PlanRootAuthorized`), and omitting it denies (`no authorized plan is configured for this verifier (set authorizedPlanRoots, or the explicit insecureSkipPlanRootCheck)`). `Authorize` decides its plan itself and passes the skip. `PcaOptions` gains `AuthorizedPlanRoots` / `InsecureSkipPlanRootCheck`; signature-only mode without either now denies every request.
  - `PcaAuthorizeOptions.Plan` defaults to null (the reference's `authorize()`): without a plan in `Context` or `Plans`, `plan_root_authorized` denies. `Plan = "single-step"` is the explicit opt-in (`PcaProtect` sets it).
  - `Authorize` enforces the risk policy of the grant: the server prices the action from the inputs IT supplies (`AuthorizeInput.ServerRisk` / `ServerRiskFor`, `PcaAuthorizeOptions.ServerRisk` / `ServerRiskFor`; a missing or non-finite input is its worst case), a signed `caution` can only raise the risk, the trust budget (`IBudgetStore`, kept per grant with the replay claim; `MemoryStateStore` and `SqlStateStore` implement it, a store without it counts as an empty budget unless `Context["budget"]` supplies one) must cover a machine-only action, and an action whose threshold is above t=1 needs `ThresholdHook` to report a verified proof at least at that t (check `threshold`). New result members `RiskScore`, `RequiredThreshold`, `Budget`; new checks `budget`, `threshold`, `risk_inputs` (`RequireRiskInputs`) and `adaptive` (`Adaptive`, a tightened policy that may only narrow). Grants whose `risk_policy` prices every action at t=1 are unaffected; every other deployment must supply risk inputs and, above t=1, a threshold hook. `Risk` (`Score`, `Required`, `Escalate`, `Leak`, `Debit`, `Recharge`, `AdmitOf`, `DecideCore`, `SubBudget`, `DebitConsolidatedPath`, `PlanGeodesic`) is public.
  - `IStateStore.Scope` (`StoreScope.Process` by default: a store must declare itself `Shared`) and `AuthorizeInput.MultiInstance` / `PcaAuthorizeOptions.MultiInstance`: true with a process-scoped store is refused (`multiInstance requires a shared state store (a process-scoped store lets one PCActn replay once per instance)`). `MemoryStateStore` is process-scoped, `SqlStateStore` shared.
  - Revocation staleness needs a store that implements `IPinStore` (`MemoryStateStore`, `SqlStateStore`; the latter creates `<table>_pin` in `EnsureSchema`) or the configuration is refused (`revocation staleness needs a state store that implements pins (rollback protection)`). The rollback pin `<grant id>:epoch` is read as a floor under the host's last accepted epoch and raised, atomically and monotonically, after an allow whose freshness check passed. `SqlStateStore.EnsureSchema` also creates `<table>_budget`.
  - `LeaseRegistry`, `BreakGlassRegistry` and `BlueprintRegistry` require a durable store (`IAtomicKv` / `IBlueprintStore`; `MemoryAtomicKv` and `MemoryBlueprintStore` are the explicit in-process ones). Documents are sharded as in the reference, any store failure is `store_unreachable`, and a registry over the same store after a restart keeps its revocations, spent budgets, freezes and disabled blueprints.
  - Middleware wire format as the reference `requirePCA`: no PCActn presented is 401 `missing_pcactn`, an undecodable or malformed one 401 `invalid_pcactn` (an unreadable body stays `invalid_request`), an unknown `grant_ref` 401 `unknown_grant`; the challenge carries a `hint`. A failed authentication check (signature, chain, audience, validity, grant binding, `pq_pin`) is 401 `invalid_pcactn`, also in signature-only mode (it was 403 `access_denied`); a policy denial stays 403.
  - `Obligations.Gate` no longer treats a JSON `null` obligations value as absent: it is refused (`obligations must be an array`); only `Obligations.Absent` is the empty list.
  - `EdKey`, `PqKey` and `SuiteKey` are `IDisposable`: `Dispose` overwrites the secret with zeros and the key cannot sign afterwards.
  - RIM XML canonicalisation follows xml-crypto byte for byte (including its locale ordering of namespace declarations); a prefix redeclared to a different URI and a non-ASCII prefix are refused.
  - `AllocationsMonotone` reports a non-array caveat list as `malformed caveats`.
- **Security (0.5 hardening):**
  - Server-side PQ pins: `AuthorizeInput.PqPins` / `PcaAuthorizeOptions.PqPins` (check `pq_pin`): a pure-PQ or hybrid grant is trusted only under a byte-equal pin for its issuer (`no server-side PQ pin for the grant issuer (suite <alg>)`, `the grant pq_pk does not match the server-side pin`); an Ed25519 grant has none to pin. Failing it is an authentication failure (401).
  - RSA public keys must have a 512..16384 bit modulus and an odd exponent from 3 to 32 bits at every RSA key (certificates, JWKs, Sigstore log keys); a certificate OID content over 256 bytes or 64 arc groups, more than 8 RFC 3161 timestamps in a Sigstore bundle, and an attestation JSON segment over 16 MiB are refused; an RSASSA-PSS issuer key must carry the restricted parameters.
  - NVIDIA and Intel attestation configuration is typed (`firmware` an object, string minimums, deny lists and `requireCrlIssuers` arrays of strings, `leafSubjectIncludes` a string, non-object `collateral`) and refused otherwise; a certificate with unparseable extensions counts as requiring a CRL.
  - `Authorize` options added from the reference: `EnforceFreshness` (`FreshnessGate`, check `freshness`: a missing, stub, future or stale signed anchor), `ResolvePrincipal` / `RequireVerifiedPrincipal` (check `principal`), `RequirePassport` / `Passport` (check `passport`, decided before the replay counter is spent).

- Fix (parity with the reference, all fail closed), found by the differential oracle tests:
  - Obligations: the refusal of a non-string `kind` names the value as JavaScript `String()` does (`undefined`, `null`, `5`), not `?`.
  - Sigstore: a leaf certificate's TBS must have the X.509 shape (version, serial, signature AlgorithmIdentifier, issuer and subject Names, a two-time validity, SubjectPublicKeyInfo, then only the optional unique-ids and extensions) and the outer signature algorithm must be an AlgorithmIdentifier; a malformed leaf is now `cert_parse` instead of failing later as `cert_chain`.
  - Issuing: when both `provenance` and `model_polarity` are malformed, `MintGrant` reports `provenance` first, as the reference does.
  - Actions: the integer-role refusal names the role (`<param>: role <role> requires an integer parameter`).
  - Approval: `Psd2Linking` refuses any truthy `unreviewed` marker (was: only `true`), reads a missing field member as absent (a refusal, not an exception), accepts `-0` minor units as 0, and leaves an absent `ccy` / `exp` out of the result; render shape refusals name the member path (`render.v`, `field.id`, `unit.ccy`).
  - Undo windows: `CompensationDigest` and `SignToken` refuse a record missing a bound member (nothing is digested or signed over an absent member); `TokenCheck` with no record is `malformed`; `DecodeToken` drops one leading BOM; a retry from a negative attempt count is a malformed record.
  - Actions: `review.provenance` (the importer's advisory suggestion record) is accepted and validated; a dismissal reason of only U+001C..U+001F is blank; a def attestation needs a string `facts_digest`; `Effective` refuses a declared trait the registry does not know even when unconfirmed; profile and reviewer-pin integers accept `-0` as 0; rule 22 and the schema verb floor check read an untrusted verb with the reference's JavaScript semantics (absent or null reversibility, non-object params, one-element arrays) so every refusal matches; refusal texts carry the reference's wording (trait ids, floors, custom trait redefinition).
  - Actions: attestation and confirmation refusals follow the reference's order and wording (no verdict changes): an attestation's facts_digest and shape are checked before its digests and it refuses in its own words (`the attestation time`, `the attestation signature`); a confirmation's `ts` and `reviewer_kid` are checked before the carried traits; an array confirmation is `unsigned`; pins that are not an object are `bad pins`. Rule 22 refusals tell null from absent (`reading 'includes'`, `reading 'slice'`) and name a null role (`reading 'startsWith'`).
  - Action registry: an absent `from` / `to` / `prev` is malformed (absent is not null); a registry key without a kid never matches; `DecidePin` refuses non-array `records` / `reapprovals` and a missing grant as `bad_pin`; a shard that is present but not an object is a digest mismatch, not a missing shard; tiers accept `-0`.
  - Authorize: a counter the stream already passed is a replay (deny), never an escalation; an escalation answer with no pinned principal is judged (and refused with that reason), never ignored; `ToolCall.ToolSignature` (new, optional) is checked against the caveat's `signature_digest`; `ValidateRiskPolicy` reads a JSON array as an object with no members.
  - Mesh: a head or proof that does not canonicalize (a lone surrogate) is `malformed head` / `malformed proof`, not a signature failure.
  - Sigstore: the leaf certificate is parsed like the reference (exactly tbs/algorithm/signature, strict extension shape, the subjectAltName read by the verifier and decoded when the issuer is checked), TLV lengths as the reference reads them, SCT timestamps at or above 2^63 only under an open-ended log key, a present `rawBytes` (even null) goes to the base64 check, and `mediaType` text as the reference prints it.
- Fix (fail-closed): `Approval.MinorToDecimal` refuses an amount above 2^53-1 (it was rendered, so an approval could show an amount the reference refuses). The `Actions` param-name refusal now reads `param name '<name>' is malformed (a-z, 0-9, _ and up to 3 dotted segments)`, as the reference. - **New (provenance by default, security default):** `Authorize` / `AuthorizeAsync` always run the new `provenance_flow` check. A sensitive action whose choice or sink arguments do not derive from the principal escalates; a forged, malformed or unbound provenance bundle, or an undecodable `PCA-Provenance` header, denies. Configure it with `AuthorizeInput.ProvenanceFlow` (`ArgProvenanceOptions`: mediator pins, action facts, server observations) and present the bundle with `AuthorizeInput.Provenance`; `PcaMiddleware` reads the `PCA-Provenance` header or the JSON body member `pca_provenance` (`PcaAuthorizeOptions.ProvenanceFlow`). The grant envelope may name mediator pins and is the only opt-out (`provenance: {mode: "insecure_off"}`, reported `not-enforced`). New `ArgProvenance` (`Decide`, `OccursAsToken`, `Leaves`, `IsReadOnlyAction`, `ReadBundle`, `PrincipalDirect`, wire validators), `ProvenanceRecorder`, `ProvMediatorPin`, `ProvObservation`, `ArgProvenanceDecision`. Servers that authorize sensitive actions without a bundle now see `escalate`: record a principal-direct bundle for calls your own UI makes. `PcaExecutor.Run` / `RunAsync` take an optional per-call bundle. Replays `arg-provenance-vectors.json`.
- **New (undo windows):** `UndoWindows` (compensation digest, signed undo token, signed receipt chain, record transitions, window clamp; replays `undo-vectors.json`), the `undo_window` obligation kind, and the optional `AuthorizeInput.Undo` / `PcaAuthorizeOptions.Undo` admission hook: an unanswered, non-provenance escalation that your undo coordinator admits becomes an allow carrying `AuthorizeResult.Undo` and the `undo_window` obligation (`AuthorizeResult.Obligations`).

- **New (agent-side signing, C-620, C-621):** the SDK now produces proofs, not only verifies them: keys (Ed25519 and the post-quantum suites it can sign), `mintGrant` / `delegate` / `commitPlan` / `buildPCActn`, discharges, narrow blocks, escalation answers, passports, workflow commitments and step receipts, read and aggregate grants, `fresh_at` tokens, and a high-level `Agent` (counter, nonce, `PCA-Action` header, delegation). Replays `producer-vectors.json` byte for byte and cross-verifies the reference's PCActns. See "Acting as an agent" in the README.

- Change (K5, workflow gate order and middleware): `Authorize` / `AuthorizeAsync` now refuse a required-and-absent workflow step (403, check `workflow`) BEFORE decoding the PCActn, and an undecodable PCActn is 401 with check `pcactn` and reason `undecodable PCActn: ...` (was check `wire`, `wire: PCActn could not be decoded`; an absent PCActn stays `wire: no PCActn presented`), so the gate never judges an unreadable proof. `PcaMiddleware` reads the workflow step from `PcaAuthorizeOptions.WorkflowCall`, else from the JSON body member `workflow` {commitment, receipts, step, units, goal_digest} when the PCActn came in the body (a present but malformed member is an empty call, which the gate denies). - **Breaking (K5, security default flip):** `plan_root_authorized` is enforced by default. - R6-05 (robustness): `VerifyChain` and `VerifyPcactnCore` are total (a malformed input is a verdict, never an exception); the per-hop type check now also requires `alg` / `pq_pk` / `pq_sig` to be absent or strings, like the reference (a hop with a numeric `pq_pk` was accepted).
- R6-02 (security): a signer-set role that registers a `pq_pk` now REQUIRES a PQ (pure or hybrid) threshold share; an ed25519-only share for that role is refused, so an Ed25519 break no longer forges a hybrid-registered role (parity with the TypeScript reference). Corpus: `agent-bound-signerset-with-pq-pk` is now `valid:false`; new positive `agent-hybrid-signerset-with-pq-pk`.
- R5-A1 (security): threshold-share verification is now signer-set PINNED, no longer self-vouched. The share must be for the one key the signer set registers for its role, a PQ/hybrid share verifies only under the set's registered `pq_pk` (a differing share `pq_pk` is refused), the share-suite tag is part of the signed bytes (a classical share cannot be relabelled hybrid), and the signer-set hash now includes a registered `pq_pk` (parity with the TypeScript reference). New corpus vectors: `agent-not-in-signer-set`, `agent-bound-signerset-with-pq-pk`, `agent-hybrid-relabel-*`.
- R5-A1 also: `SignerSetHash` previously omitted `pq_pk`.

- Suite policy defaults documented: no list = no restriction, an empty list refuses everything, and the hosted API defaults to ed25519 + Ed25519 hybrids (README lists the exact list to pass offline).

- **R4-01: root PQ pin for `Pca.VerifyChain`.** The standalone chain verifier used to verify a non-Ed25519 root hop
  (pure `ml-dsa-65` or `hybrid-ed25519-ml-dsa-65`) under the root's OWN `pq_pk`, so an attacker-minted root naming a victim
  Ed25519 issuer, signed with the attacker's own ML-DSA key, verified. `VerifyChain` now takes two optional trailing
  parameters, `IReadOnlyDictionary<string,string>? pqPins` (root issuer Ed25519 b64u -> PQ public key b64u) and
  `Dictionary<string,object?>? trustedRoot` (the verifier's own stored root capability). A root whose suite carries a PQ key
  is accepted only if `trustedRoot` has the same content hash as the root (its `pq_pk` is used), else `pqPins` has an entry
  for `root.issuer` that equals the root's `pq_pk` exactly (a differing pin is a refusal); otherwise it is refused with
  `hop 0: root suite '<alg>' needs a PQ key pinned for the root issuer (policy.pqPins) or the verifier's stored grant
  (policy.trustedRoot); the root's own pq_pk proves nothing about who issued it (R3-01)`. Ed25519 roots are unaffected.
  Check order at hop 0: shape, expected issuer, `allowedSuites`, root PQ authority, signature.
  Migration: callers of the standalone `VerifyChain` with PQ/hybrid roots must pass `pqPins` or `trustedRoot`. The PCActn
  path (`VerifyPcactnCore` / `VerifyRaw`) is unchanged: it passes its grant as `trustedRoot`.
- All PQ verification now goes through one key-resolution function that mints an opaque private `PinnedPq`; the low-level
  suite verify accepts only that type. `VerifySuiteSig` (threshold shares, pq_artifact primitives) is explicitly
  caller-vouched.
